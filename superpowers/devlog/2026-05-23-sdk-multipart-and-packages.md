# SDK: multipart support and move to packages/

**Branch:** feat/multipart-sdk  
**Date:** 2026-05-23

## Context

The SDK was generated entirely from the backend using a script + nunjucks templates. Every route — including the client runtime (auth, fetch, validation) — was rendered from templates into a single generated file consumed by the frontend.

## What changed

### 1. Introduced `packages/` and moved the SDK there

Created `packages/sdk/` as the new home for the SDK. The frontend imports it via a `file:` path in `front/package.json`:

```json
"statox-api": "file:../packages/sdk"
```

The key shift: the runtime code (HTTP client, error handling, input/output validation) moved out of nunjucks templates and into plain TypeScript at `packages/sdk/src/client.ts`. The backend generation script still runs and still produces `packages/sdk/src/generated/routes.ts`, but that file now only contains schemas and thin route wrappers — it delegates all real work to the TypeScript client.

This means the client logic is now type-checked, testable, and editable without touching templates.

### 2. Unified the route template and `_fetch` signature to support file uploads

Before this MR the SDK had no concept of file uploads. Adding multipart support required a decision: separate code paths for JSON routes vs file routes, or a single unified interface.

We went with a single `_fetch` signature:

```typescript
_fetch(path, body, file, validation, options, auth)
```

`file` is `File | Blob | null`. When non-null, the body fields are sent as `FormData` (multipart); when null, the body is sent as JSON. The generated route wrappers pass `file` through transparently, so the caller decides — the client doesn't need to know which mode a given route uses.

This also allows us to keep a single nunjucks route templates instead of two (one for JSON, one for multipart).

### 3. Superagent experiment — reverted due to mime version conflict

During development we replaced `fetch` with `superagent` to get easier multipart support (`.attach()`, `.field()`). This worked locally but broke the CI build with:

```
TypeError: mime.define is not a function
```

Root cause: `superagent@10` calls `mime.define()` internally (a mime v2 API). The frontend already pinned `mime@^4.1.0` (v4 removed `mime.define`). When npm resolves the dependency tree, the hoisted `mime@4.x` wins and superagent fails at module load time — crashing every SSR-prerendered page.

Fix: dropped superagent, implemented multipart via native `FormData` + `fetch`. No transitive mime dependency, no conflict.

## State after this MR

- `packages/sdk/src/client.ts` — TypeScript runtime: `BaseAPIClient`, `ApiError`, `APIClient` factory
- `packages/sdk/src/generated/routes.ts` — generated by `cd back && npm run generate:sdk`; schemas + route wrappers only
- `packages/sdk/src/types.ts` — shared types (`FetchFn`, `AuthType`, etc.)
- `packages/sdk/tests/client.test.ts` — unit tests with sinon stubs for fetch; 18 tests covering auth, errors, multipart, validation
